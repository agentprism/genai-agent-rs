**Q:** Okay now building on this, assuming we have now built an idiomatic rust port of pi-ai along these seams and want to port pi-agent-core next, what are the architectural seams of pi-agent-core that I should preserve in an idiomatic rust port?

## Architectural seams in `pi-agent-core` to preserve in a Rust port

`pi-agent-core` is layered into three tiers, each a distinct seam: `agentLoop` (a stateless loop function — context in, event sink, new messages out, no self-state), `Agent` (a stateful wrapper owning the transcript, queues, abort, and listeners), and `AgentHarness` (durable orchestration over sessions, lanes, and operations), plus a set of environment abstraction traits (`FileSystem`/`Shell`/`ExecutionEnv`). Preserve the boundaries between them rather than collapsing into one "agent" struct — each tier is consumed independently today: the coding agent uses the loop functions directly, UIs use `Agent`, and the durable product targets the harness.

### 1. `StreamFn` — the pluggable inference boundary
The agent loop depends on the LLM only through a narrow functional contract: `(model, context, options) => AssistantMessageEventStream`, which must never throw — all failures must be encoded as stream events/terminal message state. [1](#3-0)  This is the seam between your Rust `pi-ai` port and `pi-agent-core` port: the agent loop should depend on a trait/closure, not concretely on `Models`, so it stays swappable/testable (fakes, retries, custom routing).

Three consequences follow from this contract:

- **`proxy.ts` is the existence proof for the seam**: a complete `StreamFn` implemented over HTTP against a server that owns auth, speaking the event protocol with the `partial` snapshots stripped. Any Rust design that could not reimplement the proxy has broken this boundary.
- **It fixes the crate graph**: `pi-agent-core` should depend only on the pi-ai types/protocol crate, never on provider API implementations.
- **Skip the `setDefaultStreamFn()` process-global.** It exists as a JS host convenience; in Rust, pass the stream function explicitly.

### 2. `AgentLoopConfig` — hook-based extensibility over the turn lifecycle
Rather than subclassing, behavior is injected via optional callback hooks, each with an explicit non-throwing contract: `convertToLlm` (required message→LLM adapter), `transformContext` (pre-send pruning), `beforeToolCall`/`afterToolCall` (block/override individual tool calls), `shouldStopAfterTurn` (graceful stop), `prepareNextTurn` (swap context/model/thinking level between turns), `getSteeringMessages`/`getFollowUpMessages` (queue draining), and `getApiKey` (per-call dynamic credential refresh for long tool phases). [2](#3-1)  In Rust this maps to a struct of `Option<Box<dyn Fn...>>` fields or a trait with default no-op methods — the important invariant to preserve is "hooks must not throw/reject; return a safe fallback," which in Rust means these should return `Result` only where recoverable, and panics must not be allowed to unwind through the loop.

Two details of the hook design carry real semantics:

- **The queues are pull-based on purpose**: the loop *asks* for steering/follow-up messages via `getSteeringMessages`/`getFollowUpMessages` rather than having queues push into it, which is what keeps the loop free of `Agent` state. Preserve the direction of the dependency.
- **`transformContext` and `convertToLlm` are a two-stage pipeline with different jobs**: context-window management (pruning, injecting summaries) at the `AgentMessage` level first, then lossy projection to provider `Message`s. Don't merge them.

### 3. `Agent` class — stateful wrapper with two distinct injection queues
`Agent` wraps the loop with mutable `AgentState` (transcript, model, thinking level, streaming flag, pending tool calls, error) and exposes **two semantically different queues** — `steeringQueue` (injected before the next LLM call, mid-run) and `followUpQueue` (injected only after the loop would otherwise stop) — each with independent `QueueMode` (`"all"` vs `"one-at-a-time"`) drain semantics via `PendingMessageQueue`. [3](#3-2) [4](#3-3)  This steering/follow-up distinction is a real product semantic (interrupting vs. queuing), not incidental — worth keeping as two separate types in Rust rather than one generic message queue.

The drain points are precise and worth stating as invariants:

- Steering is polled once at run start (the user may have typed while the agent was idle) and again after every turn, unless `shouldStopAfterTurn` exits first. Follow-ups are polled only after tool calls and steering are both exhausted, and re-enter the outer loop.
- `continue()` is a decision ladder, not just "resume from a tool result": continuing from a transcript that ends in an assistant message drains queued steering first (skipping the initial steering poll so nothing is drained twice), then queued follow-ups, and only then errors.
- One run is active at a time — `prompt()`/`continue()` reject while a run is in flight — and idleness is well-defined: `waitForIdle()` resolves only after `agent_end` listeners settle and runtime state is cleared.

### 4. Uniform `AgentEvent` vocabulary across agent/turn/message/tool granularity
A single event enum covers four nested lifecycles — agent (`agent_start`/`agent_end`), turn (`turn_start`/`turn_end`), message (`message_start`/`message_update`/`message_end`), and tool execution (`tool_execution_start`/`update`/`end`) — all delivered through one subscription channel. [5](#3-4)  Preserve this as one Rust enum/stream so UI layers (TUI, RPC mode) don't need per-concern subscriptions, matching how `pi-ai`'s event stream seam was preserved.

Three delivery guarantees ride on this channel:

- **Emission is awaited, and that is a feature**: the event sink is async and the loop awaits it, so a slow consumer naturally backpressures the loop. A fire-and-forget broadcast channel in Rust silently discards this; use an async sink trait, or a bounded channel whose send is awaited.
- **Listener settlement is part of the run**: `agent_end` is the last event, but the run is not over until awaited listeners for it finish — `isStreaming`, `waitForIdle()`, and persistence layers rely on this.
- **State reduction precedes listeners**: `Agent` folds each event into `AgentState` before invoking subscribers, so listeners always observe post-event state.

### 5. `AgentTool` — tool contract decoupled from execution strategy
Tools declare schema (`Tool<TParameters>`), a `label`, optional `prepareArguments` (loose-args compatibility shim), an `execute()` that throws on failure (errors aren't hand-encoded into content), and a per-tool `executionMode` override. [6](#3-5)  The **execution mode is a batch-level policy** (`ToolExecutionMode`: `"sequential"` vs `"parallel"`), with the rule that any single `"sequential"` tool in a batch forces the whole batch sequential, and parallel batches still emit `tool_execution_end` in completion order but append `toolResult` messages in original assistant order. [7](#3-6)  This ordering guarantee (transcript determinism despite concurrent execution) is a subtle invariant worth explicit tests in the Rust port — likely implemented via a `JoinSet`/`FuturesOrdered` split between "completion notification" and "transcript append" phases.

Four more rules of the tool pipeline are correctness guards, not implementation detail:

- **Execution is three phases with fixed hook positions**: *prepare* (tool lookup → `prepareArguments` → schema validation → `beforeToolCall` gate, any failure short-circuiting to an immediate error result), *execute* (with streamed partial updates), *finalize* (`afterToolCall` field-by-field override). Preflight is always sequential, even in parallel mode.
- **The update callback is scoped and latched**: `onUpdate` calls after the tool promise settles are ignored, and pending update events are flushed before the result returns, so stragglers cannot emit out-of-order UI events.
- **A `"length"` stop fails the entire tool batch without executing anything.** Streamed tool arguments are finalized with a salvage JSON parser, so a truncated message can yield calls whose arguments validate but are silently incomplete; every call gets an error result telling the model to re-issue. Port this rule verbatim.
- **Tool errors never propagate**: a throwing `execute()` becomes an error tool result. The loop cannot be crashed by a tool.

### 6. Early termination as an aggregate signal, not an individual one
Both `BeforeToolCallResult.terminate` and `AfterToolCallResult.terminate`/`AgentToolResult.terminate` are *hints*; the loop only actually stops early when **every** tool result in the batch requests it. [8](#3-7)  This "unanimous vote" reduction over a batch is a specific seam to replicate exactly, not simplify to "any tool terminates."

### 7. `AgentMessage` extensibility via a closed union + app extension point
`AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]`, where `CustomAgentMessages` is an empty interface apps extend via TypeScript declaration merging so custom message types (notifications, artifacts) coexist with `pi-ai`'s standard `Message` types while still round-tripping through `convertToLlm`. [9](#3-8)  Rust has no declaration merging; the idiomatic equivalent is likely a generic `Agent<M: AgentMessage>` type parameter or an enum with a catch-all `Custom(Box<dyn Any>)`/trait-object variant, keeping `convertToLlm`'s job — filtering/mapping app messages down to LLM-visible ones — as a required, explicit boundary.

Two facts from the codebase tip the Rust design choice:

- **Sessions must serialize these messages.** The session tree stores `AgentMessage` values as JSON entries, and the harness resolves unknown entry types through registered `entryProjectors`. That favors a data-carrying `Custom { custom_type: String, data: serde_json::Value }` variant plus a projector registry over `Box<dyn Any>` (not serializable) or a pure generic parameter (which pushes serde bounds through every layer).
- **The harness's own custom roles are the reference consumers**: `bashExecution`, `custom`, `branchSummary`, and `compactionSummary`, each lowered to user messages (or dropped, e.g. `excludeFromContext`) by the `convertToLlm` in `harness/messages.ts`. Port these with the package as the canonical projector set.

### 8. Abort as data — cooperative cancellation with a normal event sequence
One `AbortController` per run, its signal threaded into the stream function, every hook, and every tool. Aborting produces the *same* event shapes as success — a terminal assistant message with `stopReason: "aborted"`, then `turn_end`/`agent_end` — never an exception or a truncated event sequence. `Agent.handleRunFailure()` even synthesizes this sequence when the loop itself fails unexpectedly, so subscribers can rely on lifecycle completeness unconditionally. In Rust: a `CancellationToken` checked at the same points (between preparation and execution, after hooks, between sequential tools), with cancellation encoded as message data rather than as a `JoinError` or a dropped future.

### 9. `AgentHarness` — a second, durable orchestration layer above the loop
Distinct from `Agent`, `AgentHarness` adds session persistence, operation locking, and crash recovery, using:
- **`Result<T, E>`** everywhere instead of exceptions, even reserving `getOrUndefined` to object types specifically to avoid falsy-primitive bugs. [10](#3-9)  This maps directly onto Rust's native `Result<T, E>` — this is the one seam Rust gets "for free," but the *typed error enums per subsystem* (`FileErrorCode`, `ExecutionErrorCode`, `CompactionErrorCode`, `BranchSummaryErrorCode`) are the pattern to keep: narrow, closed error enums per capability rather than one grab-bag error type. [11](#3-10)
- **Operation results pair outcome data with tagged rejections**: `RunResult`, `CompactionResult`, and `NavigationResult` carry an outcome (`completed | aborted | failed | suspended`) on success and a closed rejection union (`LaneBusy`, `NothingToResume`, `MissingIdentities`, `Closed`, ...) on refusal. The TS code emulates Rust here (`TaggedError`, `ok`/`err`), so this ports mechanically to `Result` plus `thiserror` enums.
- **Lanes** as named cursors into a shared conversation tree (one `main` lane by default, additional lanes for parallel subagents/threads), each owning at most one in-flight **Operation** (run/compaction/navigation) — this is the concurrency-control seam (mutex-per-lane) that should become an explicit Rust type rather than ad hoc locking.
- **`SuspendedOperation`/`resume()`** — a semi-durable resume contract for operations interrupted by crash or deferred provider responses, distinct from a simple retry — worth a dedicated state machine type in Rust. Resume validates identity first: `MissingIdentities` reports which tools and models the restored operation needs but the host no longer provides.
- **Manual drive is a first-class mode**: `drive: "automatic" | "manual"` with `peekAction()`/`executeAction()`/`runToCompletion()` exposing the run loop as inspectable, single-steppable actions (`ActionInfo`: `append_entry`, `stream_assistant`, `execute_tool`, `hook`, `sleep`, ...). This determinism is very valuable for testing; keep it.
- **Telemetry is injected, defaulting to no-op** (`TelemetryContext`, `NOOP_TELEMETRY_CONTEXT`), with typed span schemas — in Rust, a facade over `tracing` with the same optionality.

The durable state model beneath the harness — the session tree, the record log, and the recovery reducer — is its own seam, covered next. Note also that the current `AgentHarness` class is interface-first: many facade methods still return `HarnessNotImplemented`, while the session layer, reducer, and compaction functions beneath it are complete. Port the `AgentLane`/`AgentHarness` interfaces and the record protocol as the specification, not the stub bodies.

### 10. Session persistence — an entry tree plus a record log, reconciled by a reducer
The durable session format separates three kinds of state (`harness/session/types.ts`):
- **Entries** — the append-only conversation *tree*: `message`, `model_change`, `thinking_level_change`, `active_tools_change`, `compaction`, `branch_summary`, and `custom` entries, parent-linked with storage-assigned `seq`/`parentId`/`timestamp`, queryable session-wide or branch-scoped (leaf toward root).
- **Records** — the append-only per-lane operation log: `operation_started`/`operation_finished`, `step_attempt`, `tool_started` (with `replay: "never" | "safe"` governing what may re-execute during recovery), `queue_enqueued`/`queue_cancelled`, `write_deferred`, and `usage` rows. The usage ledger lives *inside* the record log.
- **Global facts** — latest-wins, non-branch-scoped state: the session name and entry labels.

Three sub-seams travel with this model:
- **Effective configuration derives from tree position.** Model, thinking-level, and active-tool changes are entries, so navigating to another branch restores that branch's configuration from the entries on its path plus harness defaults (`EffectiveLaneConfiguration`) — there is no separate config store to drift.
- **The reducer is the recovery contract.** `reducer.ts` reconstructs `LaneState` (open operation, step attempts, tool-batch progress, pending queues and writes, deferred handle) from a record slice, with an explicit corruption taxonomy (`RecordLogCorruption`: `multiple_open_operations`, `duplicate_tool_invocation`, `non_consecutive_attempt`, ...). The taxonomy separates states the single-writer protocol cannot produce — which restore must reject — from ordinary incomplete-but-recoverable prefixes, which restore resumes. Rust's exhaustive matching makes this port cleanly and more strictly.
- **Storage is a trait pair with a conformance suite.** `SessionStorage`/`SessionRepo` abstract the backend (JSONL is one implementation; `fork()` supports branch- and tree-scoped copies), and `session/testing/conformance.ts` is a generic test suite run against any backend — port it as a test harness parameterized over the storage implementation.

### 11. Compaction and branch summarization — pure functions driven by the harness
The compaction module is data-in/data-out and decoupled from the loop: `estimateTokens`/`estimateContextTokens`/`getLastAssistantUsage` for measurement, `shouldCompact()` against `CompactionSettings` (`reserveTokens`, `keepRecentTokens`), `findCutPoint()`/`findTurnStartIndex()` aligning the cut to turn boundaries, and `prepareCompaction()`/`compact()`/`generateSummary()` producing a `CompactionEntry` whose summary re-enters context as a marked message (`COMPACTION_SUMMARY_PREFIX`/`SUFFIX`), with the retained tail preserved verbatim. Branch summarization mirrors the same shape for tree navigation.

Two properties to preserve: these are free functions over entries, callable and testable without a harness; and compaction *executes as* a durable operation with a persisted `CompactionReason` (`manual | threshold | overflow`) so recovery resumes the same work — the `overflow` reason connects to pi-ai's overflow classifier, guarded by a one-shot `overflowRecoveryUsed` flag in lane state.

### 12. Environment abstraction traits — `FileSystem`, `Shell`, `ExecutionEnv`
The harness's filesystem and shell access are fully abstracted behind `FileSystem` (async, `Result`-returning, non-throwing-by-contract, symlink-aware but non-following-by-default) and `Shell.exec()`, composed into `ExecutionEnv = FileSystem & Shell`. [12](#3-11)  This is the seam that lets the harness run against a real OS, a sandboxed/remote backend, or an in-memory test double — in Rust this is a natural `trait FileSystem` / `trait Shell` pair with async-trait methods returning `Result<T, FileError>`/`Result<_, ExecutionError>`, never panicking, matching the explicit "must never throw" contract in the TS docs.

### 13. `AgentHarnessTool` — context-parameterized tools distinct from `AgentTool`
The harness's tool type isn't the same as `Agent`'s: `AgentHarnessTool<TContext, ...>` adds a resolved `TContext` argument to `execute()`, sourced from `AgentHarnessToolContextSource<TContext>` (either a static value or a per-turn zero-arg provider). [13](#3-12)  This lets harness-level tools access snapshot-scoped state (e.g., current filesystem/session) without global mutable state — in Rust, a generic `trait HarnessTool<Ctx>` with an associated `execute` taking `&Ctx` is the equivalent, and the "resolved per turn snapshot" timing detail matters for correctness under concurrent lanes.

One addition from the shipped types: harness tools also carry `replay?: "never" | "safe"`, which feeds the record log's recovery semantics (seam 10) — the tool contract and the durability contract meet on this field, so keep it on the tool type.

### 14. Skills and prompt templates as declarative, harness-owned resources
`Skill` and `PromptTemplate` are plain data resolved from disk (`SKILL.md`) or supplied by the app, formatted into the system prompt or expanded via placeholder substitution by pure functions (`formatSkillsForSystemPrompt`, `formatPromptTemplateInvocation`), kept separate from the harness's execution logic. [14](#3-13)  Keep these as free functions/pure data transforms in Rust rather than methods coupled to the harness struct, since they don't need harness state.

### 15. Curated, patchable per-request stream options
`AgentHarnessStreamOptions` is a curated subset of `pi-ai`'s `SimpleStreamOptions` that the harness owns and snapshots per turn, plus a `...Patch` variant with explicit-`undefined`-means-delete semantics for headers/metadata. [15](#3-14)  This "base options + sparse patch with deletion sentinel" pattern doesn't translate directly to Rust's `Option` (which can't distinguish "unset" from "delete"); preserve the *behavior* using an explicit patch enum per field (e.g., `Keep`, `Set(v)`, `Delete`) rather than collapsing to `Option<T>`.

The same delete-sentinel problem appears in pi-ai, where a `null` header value suppresses a provider default. Solve both once with a shared `Patch<T>` type.

class PendingMessageQueue {
    private messages: AgentMessage[] = [];
    public mode: QueueMode;

    constructor(mode: QueueMode) {
        this.mode = mode;
    }

    enqueue(message: AgentMessage): void {
        this.messages.push(message);
    }

    hasItems(): boolean {
        return this.messages.length > 0;
    }

    drain(): AgentMessage[] {
        if (this.mode === "all") {
            const drained = this.messages.slice();
            this.messages = [];
            return drained;
        }

        const first = this.messages[0];
        if (!first) {
            return [];
        }
        this.messages = this.messages.slice(1);
        return [first];
    }

    clear(): void {
        this.messages = [];
    }
}

/** Result of a fallible operation. Expected failures are returned as `ok: false` instead of thrown. */
export type Result<TValue, TError> = { ok: true; value: TValue } | { ok: false; error: TError };

/** Create a successful {@link Result}. */
export function ok<TValue, TError>(value: TValue): Result<TValue, TError> {
    return { ok: true, value };
}

/** Create a failed {@link Result}. */
export function err<TValue, TError>(error: TError): Result<TValue, TError> {
    return { ok: false, error };
}

/** Return the success value or throw the failure error. Intended for tests and explicit adapter boundaries. */
export function getOrThrow<TValue, TError>(result: Result<TValue, TError>): TValue {
    if (!result.ok) throw result.error;
    return result.value;
}

/** Return the success value or `undefined`. Only object values are allowed to avoid truthiness bugs with primitives. */
export function getOrUndefined<TValue extends object, TError>(result: Result<TValue, TError>): TValue | undefined {
    return result.ok ? result.value : undefined;
}
