# Preserved architectural seams — pi-ai (v2)

Source: Q/A with agents in the pi repo (latest commit on main), consolidated from two independent review passes over the same codebase.

**Q:** Lets say I was porting pi-ai to Rust, using the equivalent rust SDK's for the underlying inference like how pi-ai uses openai, anthropic messages, google vertex typescript sdks, what are the architectural seams of pi-ai that I should preserve in an idiomatic rust port?

**A:**

Based on the `pi-ai` architecture, here are the seams worth preserving in a Rust port. This is a purely informational architecture question, not an implementation task, so no plan is needed.

## 1. `ProviderStreams` — the wire-protocol trait boundary

Every API implementation (Anthropic Messages, OpenAI Responses/Completions, Google Vertex, Bedrock Converse, etc.) is required to implement exactly one small interface: `stream()` + `streamSimple()`, with optional `fetchDeferred`/`cancelDeferred` for async/polling APIs. [1](#2-0)  This is the seam that isolates "wire protocol" from everything else — a `Provider` doesn't know or care which SDK backs a model; it just holds a `ProviderStreams` value (or a map keyed by `model.api` for mixed-API providers like GitHub Copilot). In Rust, this maps naturally to a trait (e.g. `trait ApiImplementation { fn stream(...) -> Stream; }`) that each provider-specific module implements against its own SDK/HTTP client.

Two details of this contract matter for the port:

- **`DeferredHandle` is plain, serializable data** — a provider token plus whatever conversion data the API needs to reconstruct the final message later (`packages/ai/src/types.ts`). The harness in `pi-agent-core` persists it across process restarts to resume suspended runs, so the Rust type must round-trip through serde with no live objects inside.
- **Runtime failures surface *inside* the returned stream, never as a thrown error.** Even a dispatch failure ("no API implementation for X") is wrapped into a terminal error event by `lazyStream()`. See seam #12; the practical consequence is that the trait's stream methods should not return `Result` for request failures.

## 2. Provider vs. API — two independent axes

The README is explicit that "provider" (auth + model catalog + base URL) and "API" (wire protocol) are orthogonal: multiple providers share one API implementation (xAI, Groq, Cerebras, OpenRouter all use `openai-completions`), and one provider can dispatch across multiple APIs. [2](#2-1)  `createProvider()` composes `{ id, auth, models, api }` where `api` is either a single `ProviderStreams` or a `Partial<Record<Api, ProviderStreams>>`. [3](#2-2)  Preserving this two-axis design avoids the trap of coupling "provider" and "SDK" 1:1, which real providers don't respect (e.g. Codex uses OpenAI-shaped auth but a bespoke Responses variant).

### Follow-up: clarifying the two halves of this seam

**Q:** Can you clarify seam #2 in pi-ai, specifically "multiple providers share one API implementation (xAI, Groq, Cerebras, OpenRouter all use openai-completions), and one provider can dispatch across multiple APIs. "? An demonstrative example would be helpful.

**A:** This is exactly the two halves of seam #2, and the actual source files make it concrete.

#### Half A: many providers, one shared API implementation

`Provider` is a bundle of `{ id, auth, models, api }` where `api` is a `ProviderStreams` value — the wire-protocol implementation. Multiple providers can hand `createProvider()` the *same* `ProviderStreams` value (`openAICompletionsApi()`) while differing only in `id`, `baseUrl`, and `auth`:

```typescript
// packages/ai/src/providers/cerebras.ts
export function cerebrasProvider(): Provider<"openai-completions"> {
    return createProvider({
        id: "cerebras",
        name: "Cerebras",
        baseUrl: "https://api.cerebras.ai/v1",
        auth: { apiKey: envApiKeyAuth("Cerebras API key", ["CEREBRAS_API_KEY"]) },
        models: Object.values(CEREBRAS_MODELS),
        api: openAICompletionsApi(),
    });
}
``` [1](#5-0)

`groq.ts`, `deepseek.ts`, `fireworks.ts`, `together.ts`, `xiaomi.ts`, `zai.ts`, and many others follow the identical pattern — each imports `openAICompletionsApi` from the same module and only varies id/baseUrl/auth/model catalog/compat flags. [2](#5-1)

The `openai-completions` module itself absorbs the differences between these "OpenAI-compatible" backends through declarative `compat` flags on each `Model` (e.g. `maxTokensField`, `thinkingFormat`, `supportsDeveloperRole`) rather than each provider file reimplementing streaming/parsing logic. You can see this in the generated catalog code, e.g. Z.ai coding-plan models set `api: "openai-completions"` plus a `compat` block with `thinkingFormat: "zai"`: [3](#5-2)  and OpenCode variants similarly select `api = "openai-completions"` with per-model `compat` overrides depending on the underlying SDK npm package they were derived from. [4](#5-3)

So: **one implementation module, N provider identities**, differentiated by config data, not code.

#### Half B: one provider, multiple API implementations

GitHub Copilot is the concrete "mixed-API provider" example. It's a single `Provider` whose `api` field is a *map* keyed by `Api`, not a single `ProviderStreams`:

```typescript
// packages/ai/src/providers/github-copilot.ts
export function githubCopilotProvider(): Provider<"anthropic-messages" | "openai-completions" | "openai-responses"> {
    return createProvider({
        id: "github-copilot",
        ...
        api: {
            "anthropic-messages": anthropicMessagesApi(),
            "openai-completions": openAICompletionsApi(),
            "openai-responses": openAIResponsesApi(),
        },
    });
}
``` [5](#5-4)

`createProvider()`'s dispatch logic picks the right entry from that map per-model at request time, based on `model.api`: [6](#5-5)

```typescript
const apiFor = (model: Model<Api>): ProviderStreams | undefined => single ?? byApi?.[model.api];
```

The model-generation script shows *why* Copilot needs this: within the single "github-copilot" provider id, different underlying models are only reachable through different upstream wire formats — Claude models go through Anthropic Messages, Grok/GPT-5/OSWE/MAI-Code models require the Responses endpoint, and everything else uses Chat Completions:

```typescript
const isCopilotClaude = /^claude-(haiku|sonnet|opus)-[45]([.\-]|$)/.test(modelId);
const needsResponsesApi = modelId.startsWith("grok-") || modelId.startsWith("gpt-5") || ...;
const api: Api = isCopilotClaude ? "anthropic-messages" : needsResponsesApi ? "openai-responses" : "openai-completions";
``` [7](#5-6)

This is confirmed by type-level tests asserting specific Copilot models resolve to specific APIs: [8](#5-7) , and by request-level tests showing that once dispatched, a Copilot Claude model gets fully Anthropic-shaped auth/headers/payload (Bearer auth via `authToken`, Anthropic Messages payload shape) despite sharing the "github-copilot" provider id with GPT-5/Grok models routed elsewhere: [9](#5-8)

#### Why both halves matter for the Rust port

The takeaway for your Rust port: don't model "provider" and "wire protocol" as a 1:1 enum or a single trait object per provider. You need:

- A `ProviderStreams`/`Api` trait implemented once per wire protocol (`OpenAiCompletionsApi`, `AnthropicMessagesApi`, `OpenAiResponsesApi`, ...), reusable by construction across many `Provider` structs (Half A).
- A `Provider` type whose API dispatch is either "one API for all models" or "a map from `Api` → API impl, looked up per-model at request time" (Half B) — i.e. `enum ApiDispatch { Single(Box<dyn ApiImpl>), ByApi(HashMap<Api, Box<dyn ApiImpl>>) }`, with the per-model `model.api` field driving the lookup exactly as `apiFor()` does in TS. [10](#5-9)

If you collapse this to "each provider owns exactly one API implementation," you lose the ability to model GitHub Copilot / OpenCode Zen correctly, since their model catalogs genuinely span multiple upstream wire protocols under one auth/account identity.

```typescript
export interface CreateProviderOptions<TApi extends Api = Api> {
    id: string;
    /** Display name. Default: `id`. */
    name?: string;
    baseUrl?: string;
    headers?: ProviderHeaders;
    /** Required — every provider has auth semantics, even ambient/keyless ones. */
    auth: ProviderAuth;
    /** Static baseline model list (empty for purely dynamic providers). */
    models: readonly Model<TApi>[];
    /** Fetch a dynamic model overlay. createProvider restores and publishes it transactionally. */
    fetchModels?: (context: RefreshModelsContext) => Promise<readonly Model<TApi>[]>;
    filterModels?: (models: readonly Model<TApi>[], credential: Credential | undefined) => readonly Model<TApi>[];
    /** Single implementation, or map keyed by `model.api` for mixed-API providers. */
    api: ProviderStreams | Partial<Record<TApi, ProviderStreams>>;
}

/**
 * Builds a provider from parts. Built-in provider factories and models.json
 * custom providers both go through this. A single `api` streams all models;
 * an `api` map dispatches on `model.api`, and a model whose api has no entry
 * produces a stream error.
 */
export function createProvider<TApi extends Api = Api>(input: CreateProviderOptions<TApi>): Provider<TApi> {
    const baselineModels = input.models;
    let dynamicModels: readonly Model<TApi>[] = [];
    const fetchModels = input.fetchModels;
    const currentModels = (): readonly Model<TApi>[] => {
        const merged = [...baselineModels];
        for (const model of dynamicModels) {
            const index = merged.findIndex((entry) => entry.id === model.id);
            if (index >= 0) merged[index] = model;
            else merged.push(model);
        }
        return merged;
    };
    const single =
        typeof (input.api as ProviderStreams).stream === "function" ? (input.api as ProviderStreams) : undefined;
    const byApi = single ? undefined : (input.api as Partial<Record<string, ProviderStreams>>);

    const apiFor = (model: Model<Api>): ProviderStreams | undefined => single ?? byApi?.[model.api];

    const dispatch = (
        model: Model<Api>,
        run: (streams: ProviderStreams) => AssistantMessageEventStream,
    ): AssistantMessageEventStream => {
        const streams = apiFor(model);
        if (!streams) {
            return lazyStream(model, async () => {
                throw new ModelsError("stream", `Provider ${input.id} has no API implementation for "${model.api}"`);
            });
        }
        return run(streams);
    };
```

## 3. `Provider` trait — the runtime unit

`Provider<TApi>` bundles identity, `auth: ProviderAuth`, synchronous `getModels()`, optional `refreshModels()`/`filterModels()`, and the stream methods. [4](#2-3)  Note the hard requirement that *every* provider declares auth semantics, even keyless/ambient ones (local servers still return a resolvable no-op `ApiKeyAuth`) — this keeps the auth-resolution code path uniform with no special-casing for "no auth" providers.

Two smaller contracts ride on the trait:

- **`getModels()` must not throw** — `Models` treats a throwing implementation as having no models. In Rust this is an infallible method returning a possibly-empty slice, not a `Result`.
- **`filterModels()` is credential-scoped availability policy**, distinct from the catalog: GitHub Copilot uses it to narrow the model list to the OAuth credential's `availableModelIds`. `getModels()` stays the complete catalog; `Models.getAvailable()` applies the filter after confirming auth.

## 4. `Models` collection — orchestration is provider-agnostic

`Models` is the router: it holds a set of `Provider`s, does auth resolution and locking, and dispatches every `stream`/`complete`/`streamSimple` call to the provider owning the target model. [5](#2-4)  Auth resolution (`getAuth`), OAuth refresh-under-lock, dynamic model refresh (`refresh()`), and login/logout are all implemented once here rather than per-provider — this is the seam that lets `login()`/`refresh()`/`checkAuth()` be uniform across OAuth and API-key providers. [6](#2-5)

Three implementation contracts here are easy to miss and worth porting deliberately:

- **Auth application has a fixed layering order** (`applyAuth` in `packages/ai/src/models.ts`): resolved provider auth first, explicit request options winning per-field, and the `Models`-only `transformHeaders` hook running last. A `null` header value *suppresses* a provider/API default header of the same name, so a plain `HashMap<String, String>` loses information — the header value type needs a delete sentinel (e.g. `Option<String>` with `None` meaning "suppress").
- **Dynamic model refresh has deliberate concurrency semantics**: per-provider generation counters, newer refreshes superseding and aborting older ones, and publications serialized through a per-provider chain with generation checks, so a stale fetch can never clobber a newer catalog. The tests in `models-runtime.test.ts` and `providers.test.ts` encode these guarantees (see the citations under seam #11's follow-up); port the tests along with the code. In Rust this fits a small per-provider state machine or actor rather than ad hoc locking.
- **`ProviderEnv` overlays process env** for regional settings, endpoint placeholders, and proxy variables. Keep environment access injected rather than read ambiently inside API implementations — this is what makes multi-tenant hosts and tests possible.

## 5. Streaming event model — a single normalized event enum

Regardless of provider, all API implementations parse their provider-specific SSE/WS payloads into a **standardized event vocabulary** (`text`, `tool_call`, `thinking`, `usage`, `stop`, `done`, `error`), delivered through `AssistantMessageEventStream`, which is both an `AsyncIterable` and exposes a `result(): Promise<AssistantMessage>` for the terminal value. [7](#2-6)  The generic `EventStream<T, R>` base class (push/end/async-iterate, with a `finalResultPromise` resolved on a completion predicate) is a small, deliberately provider-agnostic streaming primitive. [8](#2-7)  In Rust this is your `Stream<Item = AssistantMessageEvent>` + a oneshot/future for the final `AssistantMessage` — keep the event enum unified so agent-loop code (`pi-agent-core`) never branches on provider.

Three properties of the stream primitive to carry over:

- **Events are `contentIndex`-addressed block deltas**: `start`, then `{text,thinking,toolcall}_{start,delta,end}` against an indexed content array, then a terminal `done`/`error`. This addressing is what makes the protocol renderable incrementally and serializable over a wire.
- **Make the `partial` snapshot derived, not carried.** Each TS event carries a full `partial: AssistantMessage`, which is free under JS shared references but a clone per delta in Rust. The codebase already shows the snapshot is redundant: `pi-agent-core`'s proxy protocol (`ProxyAssistantMessageEvent` in `packages/agent/src/proxy.ts`) strips `partial` from every event and reconstructs the message client-side. Make the partial-free protocol canonical and provide an accumulator (`MessageBuilder::apply(event)`) for consumers that want snapshots — the in-process and wire protocols then become identical.
- **Keep the single-consumer and terminal-value semantics**: one iteration pass, a `result()` future resolvable independently of iteration, and a terminal event that closes the stream.

## 6. Auth as a first-class, provider-owned but centrally-orchestrated concept

- `ProviderAuth` = `{ apiKey?: ApiKeyAuth, oauth?: OAuthAuth }`; providers declare which methods they support. [9](#2-8)
- `OAuthAuth` is a small three-method contract (`login`, `refresh`, `toAuth`) that's identical across Anthropic/Codex/Copilot/OpenRouter/etc., letting `Models` orchestrate login/refresh generically without per-provider special cases. [10](#2-9)
- `resolveProviderAuth()` centralizes the precedence rules (explicit override → stored credential → OAuth refresh-if-needed → env fallback), independent of which provider is being resolved. [11](#2-10)
- `CredentialStore` is a pluggable persistence interface (`read`/`list`/`modify`/`delete`), with per-provider write serialization; the default is `InMemoryCredentialStore`, and `pi-coding-agent` swaps in an `auth.json`-backed implementation. [12](#2-11)

This separation (auth *policy* orchestration vs. auth *storage* vs. per-provider OAuth *mechanics*) is worth preserving as three distinct Rust modules/traits.

Two locking details matter for correctness:

- **OAuth refresh runs under the store lock.** `CredentialStore.modify()` serializes writes per provider id, and the refresh closure re-checks expiry inside the lock, so concurrent requests never double-refresh or clobber a newer token. In Rust: a per-provider async mutex (or actor) around a `modify(FnOnce) -> Credential` primitive, not separate read/write calls.
- **A failed OAuth refresh preserves the stored credential** — re-login fixes it, and `ModelsError` distinguishes code `"oauth"` (token refresh failed; re-login is the remedy) from `"auth"` (key resolution or store failure). UIs branch on this taxonomy; keep it.

## 7. Lazy SDK loading as an explicit wrapper, not incidental laziness

`lazyApi()` wraps a `() => Promise<ProviderStreams>` loader so that importing a provider factory does not pull in its SDK until first use — critical for bundle size / tree-shaking in JS. [13](#2-12)  In Rust, the equivalent concern is usually just Cargo feature flags per provider/SDK dependency rather than runtime laziness — worth preserving conceptually (compile-time opt-in per backend) even if the mechanism differs.

### Follow-up

**Q:** For "Lazy SDK loading as an explicit wrapper, not incidental laziness", Rust doesn't need this because its already so small, and there's no web dependency, right?

**A:** Right — the runtime mechanism solves a JS-specific problem (bundle size, tree-shaking, import cost) and should not be ported. What should survive is the property the mechanism provides: backends you don't use cost nothing, and a `Provider` is constructed from an API implementation *value*, so hosts and a `models.json`-equivalent can wire any enabled backend to any provider identity at runtime. Concretely: a lean core crate holding the types and event protocol (which `pi-agent-core` depends on), API implementations behind Cargo features or in sibling crates (each heavyweight SDK dependency — e.g. the AWS SigV4 stack for Bedrock — gated with its API), and `create_provider` accepting the implementation as a value exactly as `createProvider()` does. If a Rust design makes an API implementation reachable only through a compiled-in provider enum, this seam is gone even though "lazy loading" was never the goal.

## 8. `StreamOptions` / `ApiOptionsMap` — typed per-API options with a shared base

A common `StreamOptions extends ProviderRequestOptions` covers cross-cutting concerns (signal, headers, retries, timeouts, transport, cache retention, sessionId) [14](#2-13) , while `ApiOptionsMap` maps each known API id to its own richer options type (e.g. `AnthropicOptions`, `GoogleVertexOptions`) so callers get full typing per API while `Provider.stream()` stays generic over `TApi`. [15](#2-14)  This "shared base + per-API extension" pattern maps well to a Rust generic/associated-type design (`trait Api { type Options: AsRef<BaseOptions>; }`).

Four things live on this seam beyond the type plumbing:

- **`streamSimple`/`SimpleStreamOptions` is the provider-neutral tier, and the only tier the agent layer consumes**: `reasoning` (a thinking level), `toolChoice`, `thinkingBudgets`, `deferred`. The two-tier surface — full per-API control next to a neutral simple layer — is itself the seam; don't merge them.
- **Thinking levels are data-driven**: the `off` → `minimal` → ... → `max` scale, a per-model `thinkingLevelMap` (with `null` marking a level unsupported), and the pure helpers `getSupportedThinkingLevels()`/`clampThinkingLevel()` that let callers degrade gracefully when switching models (`packages/ai/src/models.ts`).
- **The interception hooks on the base options are the no-fork escape hatch**: `onPayload` (inspect or replace the raw request body), `onResponse`, and an injectable `fetch`. In Rust: an injected HTTP client plus async callback hooks; implementations that cannot honor an injection should reject it explicitly, as the TS docs already require.
- **`samplingParams` and `metadata` are deliberately untyped passthrough maps**, merged into the request body as-is with caller keys overriding named fields. Port them as `serde_json::Map` and resist typing them — their purpose is carrying parameters pi does not model.

## 9. Compatibility flags instead of provider-specific branching

For OpenAI-compatible third parties (Cerebras, xAI, DeepSeek, Ollama, vLLM, etc.), quirks are captured as declarative `compat` flags (`supportsDeveloperRole`, `thinkingFormat`, `maxTokensField`, etc.) rather than scattered `if provider == X` checks. [16](#2-15)  This keeps the `openai-completions`/`openai-responses` API implementations single, parameterized modules — a pattern worth keeping so N "OpenAI-compatible" providers don't turn into N near-duplicate Rust modules.

Two additions keep this seam accurate at full scale:

- **There is a compat family per API, not just the OpenAI one**: `OpenAICompletionsCompat`, `OpenAIResponsesCompat`, `AnthropicMessagesCompat` (eager tool-input streaming, cache-control on tools, adaptive thinking, allowed fallback models), and `BedrockCompat`. The TS conditional type that ties `compat`'s shape to `model.api` becomes a Rust enum with one variant per API family, plus the invariant that the variant matches the model's `api` — a `match` replaces the `hasApi()` type guard.
- **The generated catalogs are data and should stay generated data.** The `*.models.ts` files become JSON embedded via `include_str!` or codegen'd statics, produced by the same generation scripts, so catalog updates never touch API-implementation code.

## 10. `createProvider()` as the one path for both built-in and custom providers

Built-in providers and user-defined custom providers (local servers, proxies, gateways) go through the exact same `createProvider()` factory and `Provider` interface — there's no special "built-in provider" trait. [17](#2-16)  Preserving this means your Rust `Provider` trait/struct should be equally usable by both compiled-in providers and dynamically configured ones (e.g. from a `models.json`-equivalent).

This is also why `Api` and `ProviderId` are open string unions (`KnownApi | (string & {})`) rather than closed enums. Port them as newtype strings, or enums with a `Custom(String)` variant — a closed Rust enum here silently removes the custom-provider feature.

## 11. Cross-provider context + dynamic model discovery

The `Context`/`AssistantMessage` types are provider-neutral so a conversation can hand off between providers mid-session (`Cross-Provider Handoffs` in the README), and `Provider.refreshModels()` + `ModelsStore` support dynamically discovered catalogs independent of a static compiled-in list. [18](#2-17)  Handoff rests on more machinery than the neutral types alone:

- **The neutral types carry provider-fidelity fields, and losing them breaks replay**: `thinkingSignature`, `thoughtSignature` (Google), `textSignature`, `reasoningDetails`, `redacted`, `responseId`, `rawStopReason`. These are opaque round-trip payloads the same provider needs back on later turns; they must survive serialization untouched.
- **`transformMessages()` is a shared lowering pass every API implementation runs** (`packages/ai/src/api/transform-messages.ts`): same-model turns replay thinking blocks verbatim (signatures included), cross-model turns convert thinking to text and drop redacted blocks, tool-call ids are normalized per target API constraints, errored/aborted assistant turns are dropped entirely, orphaned tool calls get synthetic error results, and images degrade to text placeholders for non-vision models. This function plus the fidelity fields *is* the handoff feature. Port it as one shared pass at the API-implementation boundary, and port `cross-provider-handoff.test.ts` (generate a context per provider, replay the concatenation everywhere) as an integration suite.
- **Tools are schema data, not code**: `Tool { name, description, parameters }` with JSON-schema parameters, validated by `validateToolArguments` at the boundary. pi-ai declares tools; execution lives in the agent layer. In Rust: `serde_json::Value` or schemars-generated schemas.

**A:** ## 1. Cross-provider context + dynamic model discovery in Rust — yes, both are doable

**Cross-provider context** is just a data-format normalization problem, not something that depends on JS dynamism. The seam is:

- `Context` is provider-neutral: `{ systemPrompt?, messages: Message[], tools?: Tool[] }`, and `AssistantMessage` carries `provider`/`api`/`model` tags on itself but stores content in a normalized `(TextContent | ThinkingContent | ToolCall)[]` shape. [1](#4-0) [2](#4-1)

[3](#4-2) [4](#4-3) [5](#4-4) [6](#4-5) [7](#4-6) [8](#4-7) [9](#4-8) [10](#4-9) [11](#4-10)

/**
 * Wraps a dynamically imported API implementation module as `ProviderStreams`.
 * The module loads on first stream call; the host's import cache deduplicates
 * loads. Load failures terminate the returned stream with an error event.
 */
export interface LazyApiCapabilities {
    fetchDeferred?: boolean;
    cancelDeferred?: boolean;
}

export function lazyApi(load: () => Promise<ProviderStreams>, capabilities?: LazyApiCapabilities): ProviderStreams {
    const api: ProviderStreams = {
        stream: (model, context, options) =>
            lazyStream(model, async () => (await load()).stream(model, context, options)),
        streamSimple: (model, context, options) =>
            lazyStream(model, async () => (await load()).streamSimple(model, context, options)),
    };

    if (capabilities?.fetchDeferred) {
        api.fetchDeferred = (model, handle, options) =>
            lazyStream(model, async () => {
                const implementation = await load();
                if (!implementation.fetchDeferred) throw new Error("API does not support deferred responses");
                return implementation.fetchDeferred(model, handle, options);
            });
    }
    if (capabilities?.cancelDeferred) {
        api.cancelDeferred = async (model, handle, options) => {
            const implementation = await load();
            if (!implementation.cancelDeferred) throw new Error("API cannot cancel deferred responses");
            await implementation.cancelDeferred(model, handle, options);
        };
    }

    return api;
}

## 12. Errors as messages, not exceptions

The `StreamFunction` contract is explicit: once a stream is returned, request/model/runtime failures must be encoded in the stream as a terminal `error` event carrying a complete `AssistantMessage` with `stopReason: "error"` or `"aborted"` and an `errorMessage` — never thrown (`packages/ai/src/types.ts`). Aborting is a stop reason, not a cancellation exception. `pi-agent-core`'s `StreamFn` restates the same contract verbatim, and the retry and compaction layers depend on it. In Rust, resist making this boundary `Result`-shaped: use `Result` for pre-flight/programmer errors only, and keep runtime failure as data on the stream.

Because errors are messages, classification is string matching over `errorMessage` — by design, not as a workaround:

- `utils/retry.ts` maintains regex tables of retryable errors (rate limits, 5xx, network/transport failures, premature stream endings) and non-retryable provider-limit errors (quota, billing, subscription limits), plus a `RetryPolicy` (`enabled`, `maxRetries`, `baseDelayMs`, exponential backoff) shared by the SDK, harness, and coding agent.
- `utils/overflow.ts` maintains ~25 per-provider patterns for context-overflow detection, including heuristics for providers that overflow *silently* (z.ai accepts the request; Xiaomi MiMo truncates input and returns `"length"` with zero output).
- `maxRetryDelayMs` converts a provider-requested long wait into an immediate, classifiable failure so higher-level retry logic can surface it to the user.

The provider boundary genuinely erases type information — every SDK throws differently — so port the classifiers and their pattern tables as pure functions over the error message rather than inventing a typed error hierarchy the API implementations cannot actually populate. The structured `diagnostics` field on `AssistantMessage` (redacted provider/runtime diagnostics for failures and recoveries) is kept for observability; keep it too.

## 13. `Usage` and cost accounting as first-class data

`Usage` carries input/output/cacheRead/cacheWrite token counts, the `cacheWrite1h` split only Anthropic reports, and an optional `reasoning` subset of output tokens. `calculateCost()` implements request-wide pricing tiers (`inputTokensAbove`) and the 2× base-input pricing for 1h cache writes (`packages/ai/src/models.ts`). These are pure functions over model cost metadata and port directly — and they matter beyond display: `pi-agent-core`'s usage ledger persists `Usage` values verbatim into session records, so the type is part of the durable session format, not an in-memory convenience.

export class EventStream<T, R = T> implements AsyncIterable<T> {
    private queue: T[] = [];
    private waiting: ((value: IteratorResult<T>) => void)[] = [];
    private done = false;
    private finalResultPromise: Promise<R>;
    private resolveFinalResult!: (result: R) => void;
    private isComplete: (event: T) => boolean;
    private extractResult: (event: T) => R;

    constructor(isComplete: (event: T) => boolean, extractResult: (event: T) => R) {
        this.isComplete = isComplete;
        this.extractResult = extractResult;
        this.finalResultPromise = new Promise((resolve) => {
            this.resolveFinalResult = resolve;
        });
    }

    push(event: T): void {
        if (this.done) return;

        if (this.isComplete(event)) {
            this.done = true;
            this.resolveFinalResult(this.extractResult(event));
        }

        // Deliver to waiting consumer or queue it
        const waiter = this.waiting.shift();
        if (waiter) {
            waiter({ value: event, done: false });
        } else {
            this.queue.push(event);
        }
    }

    end(result?: R): void {
        this.done = true;
        if (result !== undefined) {
            this.resolveFinalResult(result);
        }
        // Notify all waiting consumers that we're done
        while (this.waiting.length > 0) {
            const waiter = this.waiting.shift()!;
            waiter({ value: undefined as any, done: true });
        }
    }

    async *[Symbol.asyncIterator](): AsyncIterator<T> {
        while (true) {
            if (this.queue.length > 0) {
                yield this.queue.shift()!;
            } else if (this.done) {
                return;
            } else {
                const result = await new Promise<IteratorResult<T>>((resolve) => this.waiting.push(resolve));
                if (result.done) return;
                yield result.value;
            }
        }
    }

    result(): Promise<R> {
        return this.finalResultPromise;
    }
}

export function calculateCost<TApi extends Api>(model: Model<TApi>, usage: Usage): Usage["cost"] {
    const inputTokens = usage.input + usage.cacheRead + usage.cacheWrite;
    let rates: ModelCostRates = model.cost;
    let matchedThreshold = -1;
    for (const tier of model.cost.tiers ?? []) {
        if (inputTokens > tier.inputTokensAbove && tier.inputTokensAbove > matchedThreshold) {
            rates = tier;
            matchedThreshold = tier.inputTokensAbove;
        }
    }

    // Anthropic charges 2x base input for 1h cache writes.
    const longWrite = usage.cacheWrite1h ?? 0;
    const shortWrite = usage.cacheWrite - longWrite;
    usage.cost.input = (rates.input / 1000000) * usage.input;
    usage.cost.output = (rates.output / 1000000) * usage.output;
    usage.cost.cacheRead = (rates.cacheRead / 1000000) * usage.cacheRead;
    usage.cost.cacheWrite = (rates.cacheWrite * shortWrite + rates.input * 2 * longWrite) / 1000000;
    usage.cost.total = usage.cost.input + usage.cost.output + usage.cost.cacheRead + usage.cost.cacheWrite;
    return usage.cost;
}

/**
 * Wraps a dynamically imported API implementation module as `ProviderStreams`.
 * The module loads on first stream call; the host's import cache deduplicates
 * loads. Load failures terminate the returned stream with an error event.
 */
export interface LazyApiCapabilities {
    fetchDeferred?: boolean;
    cancelDeferred?: boolean;
}

export function lazyApi(load: () => Promise<ProviderStreams>, capabilities?: LazyApiCapabilities): ProviderStreams {
    const api: ProviderStreams = {
        stream: (model, context, options) =>
            lazyStream(model, async () => (await load()).stream(model, context, options)),
        streamSimple: (model, context, options) =>
            lazyStream(model, async () => (await load()).streamSimple(model, context, options)),
    };

    if (capabilities?.fetchDeferred) {
        api.fetchDeferred = (model, handle, options) =>
            lazyStream(model, async () => {
                const implementation = await load();
                if (!implementation.fetchDeferred) throw new Error("API does not support deferred responses");
                return implementation.fetchDeferred(model, handle, options);
            });
    }
    if (capabilities?.cancelDeferred) {
        api.cancelDeferred = async (model, handle, options) => {
            const implementation = await load();
            if (!implementation.cancelDeferred) throw new Error("API cannot cancel deferred responses");
            await implementation.cancelDeferred(model, handle, options);
        };
    }

    return api;
}
