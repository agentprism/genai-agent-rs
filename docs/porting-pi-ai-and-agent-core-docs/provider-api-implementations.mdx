# Provider API implementations — the definitive list

The Rust port implements the following subset of pi-ai's API implementations,
preserving pi-ai's sourcing model: use the provider's native SDK where an
equivalent exists in native Rust, find an equivalent community crate otherwise,
and re-implement the underlying wire logic in idiomatic Rust only when neither
exists. Where pi-ai itself hand-rolls the wire, the Rust port re-implements
that wire.

Transport facts below are from the verification report further down, run
against pi commit `496185f6e4267b979e3663c45f7eb70b0c6a97b4` (2026-08-19).

## 1. `anthropic-messages.ts`

1. **Transport truth.** `buildParams()` constructs an Anthropic streaming Messages payload, including `stream: true`. The actual HTTP request is issued by `client.messages.create({...params, stream: true}, requestOptions).asResponse()` at line 576. The call is wrapped by `retryProviderRequest()`, but the SDK’s own retries are disabled with `maxRetries: 0`. ([anthropic-messages.ts:565–582](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:565), [anthropic-messages.ts:973–1007](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:973))

   The SDK is asked for a raw `Response`, not its parsed message stream. Pi reads `response.body` itself in `iterateSseMessages()`, splits and decodes SSE fields locally, converts each accepted event with `parseJsonWithRepair()`, and then consumes those events in the main loop. Partial tool arguments use `parseStreamingJson()`. ([anthropic-messages.ts:330–457](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:330), [anthropic-messages.ts:460–498](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:460), [anthropic-messages.ts:589–719](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:589))

2. **SDK drop-downs.** This is not SDK-end-to-end parsing: the SDK performs the request and error handling, but pi hand-parses the SDK-returned raw SSE body. A caller can also replace SDK transport by supplying `options.fetch`, which is passed into every internally constructed `Anthropic` client, or replace the client entirely with `options.client`. There are no separate raw-fetch calls, token-counting calls, model-listing calls, WebSockets, compression paths, or other sub-feature requests in this module. ([anthropic-messages.ts:267–271](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:267), [anthropic-messages.ts:532–564](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:532), [anthropic-messages.ts:877–970](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:877))

3. **SDK role.** `@anthropic-ai/sdk` supplies the runtime `Anthropic` client plus request/event types. Pi configures API-key, bearer/OAuth, or GitHub Copilot authentication through `apiKey`/`authToken`; supplies `baseURL`, default/beta headers, browser permission, and optional fetch; and uses the SDK’s `messages.create()` request construction. Signal and timeout are passed per request. Pi disables SDK retries and reproduces the initial-request retry policy with its abort-aware helper. ([anthropic-messages.ts:1–9](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:1), [anthropic-messages.ts:570–582](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:570), [anthropic-messages.ts:901–968](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:901))

4. **Variants and deferred responses.** The module itself has one HTTP/SSE request path. `splitDeferredTools()` and `defer_loading` concern tool-definition loading inside that same Messages request; they are not background-response APIs. The public lazy wrapper enables neither `fetchDeferred` nor `cancelDeferred`. ([anthropic-messages.ts:983–1007](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:983), [anthropic-messages.ts:1041–1058](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.ts:1041), [anthropic-messages.lazy.ts:4](/Users/vikashloomba/pi/packages/ai/src/api/anthropic-messages.lazy.ts:4))
